## What V8 does vs what libuv does
- V8 is basically an engine written in C++ which is used under the hood in browser (chrome) that compiles and executes JS code, it's also the same engine used by Node.js to also compile and execute Node.js, it uses JIT (Just-In-Time Compilation which just means the JS code is compiled and executed line-by-line after compilation and not AOT where the code is compiled fully before executed). `BUT` libuv is the core engine used by JS that makes it highly concurrent whilst being a single-threaded language, it consists of the event loop, thread pools, and APIs that help node offload I/O tasks that can be handled by the OS native async capabilities, like windows uses IOCP, linux uses epoll, and macOS uses kqueue, so libuv basically is the engine that makes JS able to handle "waiting" tasks, e.g. reading a file, waiting for a TCP handshake to be completed, for HTTP requests, and so on which can block the main thread JS uses. And if the main thread is blocked, node.js cannot handle any other task within the process, which is bad.
- Node.js can handle thousands of concurrent connections without multiple threads mainly because of libuv as i have explained above.
- If a tight cpu loop is ran in node.js, because of node.js synchronous nature, it would not be able to move on to the next lines of code basically in the program, because it's still trying to like resolve that while loop, but it's an infinite loop, there's no exit loop, so the thread just stays stuck trying to execute that part of the program forever, hence blocking the main thread.

## Why can't you make CPU-bound work non-blocking just by wrapping it in a Promise?

#### Because wrapping a CPU intensive work in promise, already treats that work as asynchronous, now here the twist, this does not magically make the program non-blocking, why? because a CPU intensive work itself takes a lot of time, and when this is placed on the callback queue, and the event loop keeps waiting for that work to be done, and this itself can take A LOT of time, hence still blocking the event loop, so that doesn't just magically fix the problem. To fix it, dedicated worker threads can handle that work, or a child process can be spawned to handle the work, rather than just wrapping it in a Promise, because the bottleneck is not waiting for tasks can can take sometime ( could be a few milliseconds or seconds) like I/O tasks, TCP-handshakes, and the like, this can be done with a Promise to make it non-blocking [ because any form of waiting in JS no matter how little the time is, is blocking ], but with CPU-intensive work, the bottleneck is computation, that is heavy and can take  a LOT of time.
